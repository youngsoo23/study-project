# 아이지넷(보닥) 면접 복기 (2026-08-03)

실제로 받은 질문과 답변, 그리고 흔들렸던 부분에 대한 모범 답안을 정리. 다음 면접 준비 시 참고.

## 1. Java 21을 쓴 이유

**당시 답변:** "8에서도 개발 가능했지만, 나중에 8에서 지원 안 하는 기능을 쓸 때 마이그레이션 비용이 커질 수 있어서 21로 시작." 근거로 스트림을 들었다가 막힘 — 스트림은 Java 8부터 있는 기능이라 21을 쓸 이유가 안 됨.

**모범 답안:**
> "Java 8은 스트림 이후 언어 차원의 큰 변화가 없었지만, 21은 LTS이면서 record·sealed class·pattern matching으로 불변 DTO와 타입 안전한 분기 처리가 쉬워지고, 특히 virtual thread로 스레드 풀 관리 부담 없이 I/O 바운드 처리량을 늘릴 수 있어서 향후 트래픽 증가 대응이나 코드 안전성 측면에서 이점이 크다고 판단했다."

**핵심 교훈:** 8에도 있는 기능(스트림)을 근거로 들면 안 됨. 21에만 있는 것(virtual thread, record, sealed class, pattern matching for switch)으로 답해야 함.

## 2. 스트림 안에서 쓸 수 있는 함수형 인터페이스

**당시 답변:** map, filter + "for문보다 가독성 좋다." → 의도했던 답이 아니라고 함.

**모범 답안:**
> "스트림 연산은 `java.util.function` 패키지의 함수형 인터페이스를 기반으로 합니다. `map`은 `Function<T,R>`, `filter`는 `Predicate<T>`, `forEach`는 `Consumer<T>`, 인자 없이 값을 만들어내는 `Supplier<T>`가 있고, 두 값을 받는 `BiFunction`, 입력과 출력 타입이 같은 `UnaryOperator`/`BinaryOperator`도 있습니다."

**핵심 교훈:** map/filter는 "쓴 메서드"일 뿐, 질문 의도는 그 뒤에 있는 함수형 인터페이스 이름.

## 4. 필터 vs 인터셉터 차이

**당시 답변:** "필터가 더 앞단이고 거기서 막아야 되는 요청이 있으면 막는다." → 스코프/동작 계층을 명확히 못 짚음.

**모범 답안:**
> "필터는 서블릿 스펙 표준으로 서블릿 컨테이너 레벨에서 동작하고, `DispatcherServlet`에 요청이 들어가기 전/후에 실행됩니다. 스프링 컨텍스트 밖이라 빈을 직접 주입받기 까다롭고, 인코딩·CORS·XSS 필터링처럼 애플리케이션 전역 공통 처리에 적합합니다. 인터셉터는 스프링 MVC 스펙으로, `DispatcherServlet`이 컨트롤러를 호출하기 전(`preHandle`)/후(`postHandle`)/완료 후(`afterCompletion`)에 개입합니다. 스프링 컨텍스트 안이라 빈을 자유롭게 쓸 수 있고, 어떤 핸들러가 호출되는지도 알 수 있어서 인증/인가나 로깅처럼 핸들러 정보가 필요한 로직에 적합합니다."

## 6. 사용 중인 고객의 토큰을 즉시 무효화하려면?

**당시 답변:** Redis에 저장해두고 데이터 삭제. → refresh token만 다룬 것으로, access token 자체는 즉시 막지 못함.

**모범 답안:**
> "Refresh token은 Redis에 저장해뒀으니 삭제하면 재발급을 막을 수 있지만, 이미 발급된 access token은 만료 전까지 유효해서 그것만으로는 즉시 차단이 안 됩니다. 그래서 access token 자체를 blacklist로 Redis에 등록합니다 — 토큰의 남은 만료 시간만큼 TTL을 줘서 저장해두고, 인증 필터에서 매 요청마다 blacklist 여부를 체크해서 있으면 거부합니다."

## 10. 가상 스레드(Virtual Thread)

**당시 답변:** 개념은 알지만("여러 스레드를 병렬로 처리") 실사용 경험 없음.

**모범 답안:**
> "기존 플랫폼 스레드는 OS 스레드에 1:1로 매핑돼서 개수가 늘어나면 컨텍스트 스위칭 비용과 메모리 부담이 커집니다. 가상 스레드는 JVM이 관리하는 경량 스레드로, 하나의 캐리어 스레드 위에 수천~수만 개를 얹어 실행할 수 있고, I/O 블로킹이 발생하면 캐리어 스레드에서 분리됐다가 완료되면 다시 스케줄링되는 방식입니다. 그래서 기존 동기 블로킹 코드 스타일을 유지하면서도 리액티브 수준의 처리량을 낼 수 있고, 특히 DB나 외부 API 호출 같은 I/O 바운드 워크로드에서 효과가 큽니다. 실사용 경험은 없습니다."

## 14. AOP 사용 경험 설명

**당시 답변:** Audit 로그 사용 경험으로 설명 — 백오피스에서 클라이언트 정보 수정/조회 시 DB에 기록 저장, API 요청마다 AOP 활용. "동일한 메서드를 여러 곳에서 쓸 때 좋다"는 취지로 설명.

**모범 답안:**
> "AOP(Aspect-Oriented Programming)는 로깅, 트랜잭션, 인증/인가, 감사 로그(audit log)처럼 여러 모듈에 공통으로 걸쳐있는 관심사(cross-cutting concern)를 비즈니스 로직 코드에서 분리해 모듈화하는 방식입니다. 예를 들어 백오피스에서 클라이언트 정보를 조회/수정할 때마다 '누가 언제 무엇을 변경했는지' 감사 로그를 DB에 남겨야 하는데, 이 로직을 매 API 메서드마다 직접 넣으면 중복되고 비즈니스 로직과 뒤섞입니다. 그래서 감사 로그 저장 로직을 `@Around` 같은 어드바이스로 분리하고, 특정 어노테이션이 붙었거나 특정 패키지 하위에 있는 메서드를 포인트컷으로 지정해서, 실제 메서드 호출 전후로 자동으로 감사 로그가 남도록 처리했습니다."

**후속 질문 — AOP는 어떤 디자인 패턴에 기반하는가**

**당시 답변:** 모른다.

**모범 답안:**
> "Spring AOP는 내부적으로 **프록시 패턴(Proxy Pattern)**으로 구현됩니다. 대상 빈이 인터페이스를 구현하고 있으면 JDK 동적 프록시를, 없으면 CGLIB으로 대상 클래스를 상속한 프록시를 만들어서, 실제 객체 대신 프록시가 호출을 가로챈 뒤 부가 로직(어드바이스)을 실행하고 실제 메서드를 호출하는 구조입니다. 즉 원본 객체를 대리 객체가 감싸서 요청을 가로채는 구조라 프록시 패턴에 기반합니다."

## 15. Record 클래스

**당시 답변:** response/request DTO로 사용해봤다. 클래스는 getter/setter를 직접 만들어야 하는데, record는 `@Data`가 이미 적재된 클래스로 알고 있다. → 역질문 "record의 다른 기능은?"에 모른다고 답함.

**모범 답안:**
> "record는 생성자, getter(필드명 그대로, `getName()`이 아니라 `name()`), `equals`/`hashCode`/`toString`을 자동 생성해주는 불변 데이터 캐리어입니다. Lombok `@Data`와 비슷해 보이지만 다른 점은, `@Data`는 setter도 만들어주는 mutable 객체인 반면 record는 필드가 모두 `private final`인 완전한 불변 객체라는 겁니다. 그 외 기능으로는 **compact constructor**가 있는데, 일반 생성자처럼 파라미터를 다시 선언하지 않고 `Money { if (amount < 0) throw new IllegalArgumentException(); }` 처럼 검증 로직만 넣을 수 있는 문법입니다. 필드 할당 코드는 컴파일러가 자동으로 추가해줍니다. 그리고 record는 기본적으로 `final`이라 클래스 상속은 안 되지만, 인터페이스 구현은 가능합니다."
